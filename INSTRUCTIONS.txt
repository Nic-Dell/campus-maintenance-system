MIDTERM PROJECT
Campus System – Round 1
Node.js and Express Web Application

1. Project Overview
For the Midterm Project, students will work in teams of three (3) to develop a functional Campus System
using Node.js and Express. Teams will be paired with another team. Both teams will be assigned the same
campus system, but each team must design and develop its own implementation independently.
The project assesses the team's ability to:
• Analyze and document system requirements.
• Design and implement a web application.
• Use Node.js and Express.
• Create pages, forms, and stored data.
• Implement basic authentication and access control.
• Work collaboratively using GitHub.
• Use branches and pull requests.
• Conduct peer code reviews.
• Follow conventional commit practices.
• Manage tasks using GitHub Issues/Projects.
• Explain and defend individual contributions.
• Evaluate another team's implementation using evidence.
Important: Your GitHub repository is part of your project. The instructor must be able to see how the
system was developed, not only the final code. A team that uploads the entire project in one large commit
at the end will not demonstrate effective collaboration.

2. Team Composition
Each team must have exactly three (3) members.
Member Suggested Primary Responsibility
Member 1 Backend / Routes / Business Logic
Member 2 Frontend / Pages / Forms / UI
Member 3 Database / Authentication / Testing
Roles may rotate, but each member must contribute significantly to the actual development. Every member
must create code, make commits, work on a feature branch, create or contribute to issues, participate in
pull requests, review another member's code, and understand the overall system.
Do not divide the project into three completely independent parts and combine everything at the end.

3. Paired Team System
Your instructor will assign two teams to the same campus system. Both teams develop the same type of
system independently.

Pair Team
Pair A Team 1 – Clinic System
Pair A Team 2 – Clinic System
Teams must not copy the other team's source code, share implementation code, reuse the other team's
repository, coordinate their implementation, or ask the other team to develop features for them.

Any additional package or framework must have a reasonable purpose in the project.

5. Minimum System Requirements
A. Multiple Pages
The system must have multiple functional pages. Examples include Login, Dashboard, List/View Records,
Add Record, Edit Record, Record Details, User/Profile, and Reports or Summary.
B. Forms
The system must contain functional forms such as login, registration, add/edit record, search, or
request/reservation forms. Forms must accept input, validate it, process the submission, store/retrieve data
when appropriate, and display an appropriate response.
C. Stored Data
Data must actually be stored and retrieved. Refreshing the page must not cause previously saved records
to disappear.
A form that only displays “Successfully submitted!” without actually storing the data does not satisfy the
stored-data requirement.

6. Basic Authentication and Access Control
At minimum, demonstrate login, session management, logout, and access restriction. Protected pages
must not be accessible to unauthorized users.
For example, an administrator may access user management while a regular user may access only their
permitted pages. A user must not be able to type an administrator URL directly and bypass authorization.

7. Input Validation and Data Handling
All user-submitted information must be checked before being stored. Validate required fields, email format,
numbers, length, duplicate records, invalid values, and credentials as appropriate. Provide useful error
messages.

8. Requirements Document
Before or during development, the team must create a Requirements Document containing:
• Users – people who will use the system.
• Stakeholders – people or groups affected by the system.
• Functional Requirements – what the system must do.
• Non-Functional Requirements – how the system should perform.
• Use Cases – usable descriptions of major functions, including actor, precondition, steps, and expected
result.

9. GitHub Repository
Each team must create one GitHub repository. A clear structure is expected, for example:
campus-system/
├── public/
├── views/
├── routes/
├── controllers/
├── models/
├── middleware/
├── config/
├── app.js
├── package.json
├── .env.example
├── .gitignore

├── README.md
└── LICENSE

10. GitHub Branching Requirement
Do not develop the entire project directly on main. Use feature branches.
main
├── feature/login
├── feature/student-dashboard
├── feature/request-form
├── feature/database
└── feature/access-control
Example commands:
git checkout -b feature/login
git add .
git commit -m "feat: implement user login"
git push -u origin feature/login
After completing the feature, create a Pull Request on GitHub.

11. Pull Requests
Every major feature should be submitted through a Pull Request. The PR should explain what was
implemented, files changed, issue addressed, and how the feature was tested.

12. Peer Code Review
A Pull Request must be reviewed by another team member before merging. Reviewers should check
functionality, code clarity, bugs, input validation, project structure, security issues, and requirements
compliance.
The review must be genuine. A generic “Looks good” on every PR without meaningful review is insufficient
evidence.

13. Conventional Commits
Commit messages must follow a consistent conventional format.
Prefix Example
feat: feat: add student registration
fix: fix: prevent duplicate student records

docs: docs: update system requirements
test: test: add login validation tests
refactor: refactor: organize route handlers
chore: chore: update dependencies
Avoid meaningless messages such as “update,” “final,” “final2,” “asdf,” or “upload project.”

14. GitHub Issues
Break the project into manageable tasks using GitHub Issues. Each issue should identify the task,
description, responsible person, and expected result. Where possible, connect commits and Pull Requests
to issues.

15. GitHub Project / Issue Board
Create an issue board with columns such as:
• BACKLOG
• TODO
• IN PROGRESS
• REVIEW
• DONE
The board should reflect the actual development status.

16. Contribution Requirement
All three members must have visible and substantial contributions. Evidence may include commits,
branches, Pull Requests, code reviews, issues, documentation, testing, and bug fixes.
Commit count alone does not determine contribution quality. The instructor may examine the actual
changes made.

17. README.md
The repository must contain a useful README with:
• Project Description
• Team Members
• Assigned System
• Features
• Technologies
• Installation
• Configuration
• Database Setup
• How to Run
• User Accounts
• Project Structure
• Known Limitations
• AI Assistance Disclosure

• License

18. Environment Variables and Security
Do not commit passwords, API keys, database credentials, or other secrets. Use .env and place .env and
node_modules/ in .gitignore. Provide .env.example instead.
Never upload actual database passwords, API keys, or session secrets to the repository.

19. License
The repository must contain an appropriate license, clearly visible in the repository.

20. AI Assistance Disclosure
If AI tools such as ChatGPT, GitHub Copilot, Claude, Gemini, or other AI-assisted development tools are
used, disclose their use. AI assistance does not remove the team's responsibility for understanding,
testing, correcting, and defending the code.

21. Application Testing
Before the showcase, test the complete system.
• Authentication: correct login, incorrect password, empty credentials, logout, unauthorized page access.
• Forms: valid input, empty fields, invalid input, duplicate data.
• Database: create, read, update, and delete where applicable.
• Access Control: test every role and verify that restricted pages cannot be bypassed.

22. Round 1 Showcase
Each team will demonstrate the completed system using the actual working application.
Part 1 – Project Introduction
• System name
• Problem being addressed
• Target users
• Main purpose
Part 2 – Requirements
• Users
• Stakeholders
• Major functional requirements
• Major non-functional requirements
• Important use cases
Part 3 – System Demonstration
Demonstrate the major end-to-end workflow using the actual system.

Part 4 – Access Control
Demonstrate login, session, role-based authorization, and an unauthorized access attempt.
Part 5 – GitHub Workflow
Show repository, branches, issues, project board, Pull Requests, code reviews, commit history, and
team contributions.
Part 6 – Counterpart Critique
Present a specific, professional, evidence-based critique of the paired team's implementation.

23. Evidence-Based Counterpart Critique
The critique must be professional and evidence-based. Do not simply say that another team's system is
“bad.” Explain the observation, evidence, impact, and recommendation.
Evaluate requirements, functionality, user experience, data handling, security, code organization, and
GitHub workflow.

24. Defense
Every member must be prepared to explain their contribution. The instructor may ask what feature you
developed, why it was implemented that way, which route handles it, where data is stored, how
authentication and roles work, how invalid data is handled, which branch/PR contains the contribution, and
what problems were encountered and solved.

25. Submission Requirements
1. GitHub Repository – instructor must have access.
2. Requirements Document – users, stakeholders, functional and non-functional requirements, and use
cases.
3. Working Application – system must run successfully.
4. README.md – installation and project information.
5. GitHub Project/Issue Board – task management evidence.
6. Evidence of Collaboration – branches, Pull Requests, reviews, commits, and issues.
7. AI Disclosure – disclose AI assistance if used.
8. License – include a valid license.
